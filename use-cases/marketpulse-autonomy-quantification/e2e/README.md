# Marketpulse autonomy quantification

This case keeps the lifecycle/reporting shape of the neighboring AgentVault Marketpulse case and replaces its payment-specific fixtures with external social/LLM boundaries. It never replaces Sigbot's internal Rust services with a Python trading pipeline.

Install the single dependency definition in a virtual environment, then use only `runner.py` to orchestrate verification:

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
.venv/bin/python -m playwright install chromium
export MARKETPULSE_MOCK_TOKEN='<local-test-token>'
.venv/bin/python runner.py --scenario structure,schemas
.venv/bin/python runner.py --deploy --scenario infra,boundaries --deployer docker --timeout 180
.venv/bin/python runner.py --scenario runtime,pipeline,recovery,logs,web --rounds 2 --reuse-build --timeout 120
```

Set `MARKETPULSE_POSTGRES_PASSWORD`, `MARKETPULSE_DATABASE_URL`, `MARKETPULSE_MINIO_ACCESS_KEY` and `MARKETPULSE_MINIO_SECRET_KEY` before infrastructure/full-chain verification. Apply the repository migrations, build the existing `sigbot` and `sigbot-strategy-worker` binaries, then run `runtime,pipeline` together. Runtime launches the existing service CLI commands with scoped configuration, injects external initial funding through MQTT, and waits for the real wallet journal; it never inserts money directly. The run ID is generated by the runner, or can be supplied through `MARKETPULSE_WORKFLOW_RUN_ID` for an existing isolated run. PG defaults to loopback port 15439, MQTT 18883 and MinIO 19000. Source endpoint/token environment names belong to the real datafeed node configuration. `config/sigbot/config.yaml` selects endpoints, scope, workflow and account; credentials are environment references. The compose broker is isolated to loopback and requires JWT authentication. Set `MARKETPULSE_MQTT_SIGNING_KEY` (at least 32 characters); the runner creates a four-hour case credential limited to the configured environment/tenant/space. The `acl` scenario requires real MQTT 5 rejection of invalid credentials and cross-scope publish/subscribe. These local broker credentials do not authenticate the Authguard UI/API. Service-role ACLs and broker crash persistence require separate acceptance.

`--scenario` is repeatable and accepts comma-separated names. Default runs all scenarios and fails if a real service is missing. Reports are under `reports/YYYYmmddHHMMSS`; only executed scenarios can pass. A passing `boundaries` run proves external protocol compatibility, not the internal pipeline. Failed or unexecuted UI/full-chain tests are never counted as successful. The stack is retained unless `--cleanup-after-run` or `--cleanup` is given. Before starting a fresh run on the same local ports, use `--stop-runtime` to stop only this case's owned product processes while retaining infrastructure and previous evidence.

Docker uses Compose, with `MARKETPULSE_COMPOSE_COMMAND` for a compatible command prefix. Kubernetes uses the required `/etc/rancher/k3s/k3s.yaml`, an isolated `sigbot-marketpulse-e2e` namespace and prebuilt boundary images. The Kubernetes case chart deploys only the three external boundaries; install the product chart for PostgreSQL/EMQX and actual Rust services, then configure/forward endpoints. `MARKETPULSE_KUBECTL_COMMAND` and `MARKETPULSE_HELM_COMMAND` may supply a local `sudo -n` prefix. Cleanup verifies namespace ownership and never removes named images.

The X fixture contract is the complete official [X OpenAPI JSON](https://api.x.com/2/openapi.json), fetched at the timestamp and SHA-256 in `config/twitter/provenance.json`. Post fixtures are synthetic and validated against that pinned schema; they are not real posts. REST pagination, API token rejection, HTTP trace propagation, actual WebSocket delivery, official MCP initialization/tool calls, official A2A messages, and deterministic OpenAI completions are exercised by `boundaries`.

No publicly accessible official Truth API OpenAPI document was found. The [official open-source page](https://help.truthsocial.com/legal/open-source/) links Mastodon sources, while the [TMTG release linked from its official site](https://www.pressviewer.com/profiles/investor/NewsPrint.asp?ID=168199&b=2660&g=1953&m=rl&v=7) announces a separately licensed Truth API. `config/truthsocial/openapi.json` is explicitly a locally authored Mastodon-compatible subset. It does **not** satisfy a claim of exact compatibility with the latest licensed Truth API. WS/MCP/A2A endpoints in both mocks are case gateways around the REST timeline model, not claims that the native platforms expose all three transports.

The sample strategy runs inside the real isolated Rust/Python worker. It waits for persisted social news and evaluator hyperparameters before emitting a bounded intent using actual public Binance market facts. Order executes against the product SimulatedExchange; no real exchange trade is placed. The pipeline verifier injects duplicate and out-of-order news only at the external boundary, observes v2 MQTT topics with QoS 1, fsyncs evidence before ACK, and reads committed market/evaluation/order/execution/wallet facts. It checks balanced postings and that `requestSpanId` was not persisted. The `recovery` scenario kills only owned strategy/order/wallet processes, restarts those exact real services, replays captured signal/execution messages, and requires financial projections to remain unchanged. The `logs` scenario checks real Python strategy stdout through the Rust WAL buffer, MinIO object hash and PostgreSQL index; it does not claim automatic capture of every Rust tracing event. These scenarios count only when actually executed successfully. General distributed model sharding, live exchange execution and exact licensed Truth API compatibility require additional evidence.

The `web` scenario captures real Chromium screenshots of navigation, notification/account panels and graph editing. `web-full` additionally requires `MARKETPULSE_BROWSER_STORAGE_STATE` from a real Authguard login, and checks actual save/start responses plus run/trace/span evidence. It deliberately fails when this authenticated session is missing. `MARKETPULSE_CHROMIUM_PATH` can point to an already installed compatible Chromium. No route is intercepted and no test login is invented.

`replay` selects a prior completed real pipeline, or `MARKETPULSE_REPLAY_SOURCE_RUN_ID`, freezes its finite history and recorded AI outputs, and creates a separate `replay-marketpulse-*` scope per execution with a new account, wallet, Workflow and run. It launches the existing Rust Backtest replay owner and Strategy, query-only Datafeed, Order and Wallet services. The verifier runs the same frozen history twice in separate scopes and compares their actual execution prices, quantities and fees. Every fill must reference a real frozen source tick. It also checks wallet posting balance, AI versions/probabilities and virtual availability, then restarts each replay owner to check idempotency. Real-time asynchronous query latency is not reproduced by the virtual clock; live-versus-replay tick equality is not the acceptance criterion. Historical rows are input data; Python does not implement the replay engine, matching or accounting. The source interval is limited to one hour and 1,000 decision steps. Failed replay attempts remain failed in the report until the complete verifier passes.

`groups` runs seven actual product processes for a two-account, same-venue scenario. The first account receives an external funding fact; the second has no capital. The real strategy emits two grouped intents, the second Wallet rejects reservation, and the coordinator emits one reverse reduce-only intent through the normal risk/order/execution/wallet chain. Verification checks both actual fills, zero residual position, exact fees/cash, then crashes the strategy, two Order workers and two Wallet workers and repeats original signals. This verifies multi-account compensation, not cross-venue acceptance. `rust-groups` separately exercises six real PostgreSQL coordinator contracts with explicitly synthetic committed participant fixtures, including partial/unknown outcomes and compensation failure.

For Rust acceptance, `rust-boundaries` runs the actual external-transport and PostgreSQL query tests. `rust-messaging` tests real broker delivery, durable replay with unchanged run/sequence, incremented attempt and fresh span, scope isolation and quarantine ACK. With `--reuse-build`, these scenarios identify compiled test binaries by their actual test names and record their SHA-256; no build is invoked. Otherwise they require Cargo and respect the target size limit; do not run them concurrently with another product build. Cleanup stops only manifest-owned processes whose binary and process start time still match, then removes only the case deployment.

`rust-policy` makes actual read-only HTTPS requests through the product FED/TREASURY RSS adapters. It requires dated official entries and propagates network failures as failures. These public endpoints are not mocked. `rust-boundaries` also checks explicit source revisions and retained canonical delivery identity in PostgreSQL. These additional gates have independent evidence; earlier full-chain reports do not imply they were executed.

`rust-market` reads actual Binance and Hyperliquid trade facts through their SDK adapters. `rust-boundaries` additionally requires active two-source LATEST persistence/reply atomicity, persisted-only AS_OF, canonical repeated requests and independent symbol checkpoints. Public network failures remain failures. The original trading scenario keeps its declared Binance instrument; the active two-source contract uses HYPE/USDC without placing orders.

Snapshot and compute callbacks use the real shared DTOs and Datafeed query runtime. PostgreSQL/TimescaleDB performs bounded window aggregation with explicit event/availability cutoffs and latest revisions. `mean-price-v1` is the explicitly registered deterministic prediction model; arbitrary Python models are rejected. Current queries recompute requested windows to preserve late-revision correctness; Redis caching and incremental shard workers are not claimed implemented. The ignored PostgreSQL contract test validates future exclusion, late revisions and sum/count partition equivalence.

The pinned MinIO release is recorded in `config/minio/provenance.json`. If its public registry image cannot be pulled, use a trusted mirror via `MARKETPULSE_MINIO_IMAGE`; the local verification used the same official GitHub binary after checking the official SHA-256. This deployment limitation must not be counted as a successful container rollout.

`kubernetes-prepare --timeout 300` builds a local verification carrier from the already built Rust binaries and the host's Python 3.12, ELF libraries, CA bundle and pinned boundary dependencies, then imports it into local K3s. It uses `FROM scratch` and records binary/root filesystem hashes; this host ABI artifact is not a portable release image and does not verify the Docker provider. No Cargo build is performed. An independent `sigbot-marketpulse-workers` namespace contains the real Twitter boundary, Secret/ConfigMap and constrained connectivity probe. Initial posts have fresh, schema-valid IDs and a fixed per-deployment event time. PostgreSQL and EMQX remain the existing isolated fixture services.

After preparation, source `/tmp/sigbot-marketpulse-workers/test.env` and run `--scenario rust-deployment --reuse-build --timeout 360` to execute the actual Rust Kubernetes provider test. Its configuration/snapshot files are mode 0600; credentials are never copied into image layers or reports. The test requires actual Datafeed delivery and Python callback checkpoints, then checks idempotent apply, configuration update, Pod recovery, removal and refusal to take over an unmanaged resource. Preparation success alone is not worker acceptance. All Kubernetes commands select `/etc/rancher/k3s/k3s.yaml`. The namespace remains for inspection; `--cleanup-workers` removes only its owned resources and generated configuration files.

`legacy-migration` verifies an upgrade with existing records in a dedicated PostgreSQL 16+ container. The default is `sigbot-migration-check`; `MARKETPULSE_MIGRATION_CONTAINER` may select another isolated container with that name prefix. `MARKETPULSE_MIGRATION_COMMAND` selects local `podman`, `docker` or their `sudo -n` form (default `sudo -n podman`). The fixture container must allow noninteractive administration as `postgres` over its local Unix socket. This gate reads no credential file and does not create/delete containers or images. It rejects containers with unrelated databases: existing names must be `postgres`, `sigbot_check_*` or `sigbot_legacy_probe_*`, and all SQL targets the verified immutable container ID.

Run `python runner.py --scenario legacy-migration --rounds 2 --timeout 120 --reuse-build`. The official `migrate.py` first applies the four 2024/2025 baseline files, imports explicitly synthetic legitimate historical records from `config/sigbot/legacy_migration.sql`, then applies all current 21 migrations and repeats the official runner. Fifteen checks cover UUID Workflow/Run mapping, retained wallet/ledger/balance/position/equity fields, 22 integral digits, foreign keys, immutable legacy ledger, no fabricated funding journal, and repeat-upgrade idempotency. Each round owns a random temporary database and removes it in `finally` on success or error; cleanup failure fails the gate and records the database name. SQL logs, rendered migration SQL, fixture/migration/runner SHA-256 and checks are written under `reports/<timestamp>/legacy-migration/`. This evidence does not replace a production data upgrade or disaster recovery rehearsal.

`rust-extensions` uses the separate `deploy/postgres-extensions/docker-compose.yaml` to run actual TimescaleDB + pgvector PostgreSQL with 1 CPU, 1 GiB and loopback port 15440. It applies all migrations and executes the independent Rust `compute_extensions` target. Build that target centrally with `cargo test -p sigbot-datafeed --test compute_extensions --no-run`, then run `python runner.py --scenario rust-extensions --reuse-build --timeout 180`. `MARKETPULSE_EXTENSIONS_COMMAND` selects local `podman`, `docker` or their `sudo -n` form (default `sudo -n podman`); the engine needs its Compose provider. Missing images are pulled by digest only after checking at least 9 GiB free disk space. This fixture pins the locally verified linux/amd64 child. Dedicated container/volume names and owner labels prevent takeover; both resources are removed on success or failure, while images and reports remain. Generated passwords exist only in a temporary 0600 file and the test subprocess environment and are removed afterwards.

The ordinary Case Compose and product Helm now pin the same official Timescale HA multi-architecture index (recorded with its verified amd64 child in `config/postgres/provenance.json`). The existing running plain-PG case was not replaced. The ordinary case explicitly uses a **new** named volume, `sigbot-marketpulse-postgres-ha-pg16-v1`; its former `postgres-data` volume remains intact. Do not run `--deploy` against existing data expecting automatic migration: back up/export, restore and reconcile into a fresh HA volume, then explicitly switch connections. HA uses `PGDATA=/home/postgres/pgdata/data/pgdata`; changing only the image while retaining the old `/var/lib/postgresql/data` mount is insufficient.

Empty-volume initialization and explicit upgrades share `tooling/deploy/helm/sigbot/bootstrap/postgres-extensions.sql`. On an existing database, an extension-owner role must explicitly run `psql --no-psqlrc --set ON_ERROR_STOP=on --file tooling/deploy/helm/sigbot/bootstrap/postgres-extensions.sql` with secure PG environment/Secret configuration; init scripts do not rerun on populated data directories. Both extension libraries must be installed and Timescale preloaded. This gate exercises actual functions and 7-day/3-day/25-hour/365-day compute equivalence against PostgreSQL `date_bin` with the same 1970 UTC origin, including late revisions and unavailable future observations. It does not prove Evaluator vector similarity retrieval, and prior plain-PG reports remain plain-PG evidence.

Helm systemdb uses the official HA UID/GID 1000 with non-root and fsGroup/OnRootMismatch. Rendering is checked; this isolated Compose gate does not verify permissions on a new Kubernetes PVC. Bootstrap explicitly fails when extension files, Timescale preloading or the installation superuser role are missing.
