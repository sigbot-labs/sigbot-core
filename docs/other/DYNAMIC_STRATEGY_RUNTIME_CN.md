# 背景与现状

- `sigbot-researcher` 已能基于 `sigbot-core` 生成静态策略代码（或 workflow + 静态策略代码）。
- 现有实盘执行链路以 `datafeed` 事件驱动为主，`strategy runner` 消费行情/新闻事件生成信号。
- 需求希望在实盘阶段引入动态 AI/工具调用能力，允许策略超参与信号判定逻辑在准实时数据基础上动态计算，并与静态策略代码混合执行。

# 目标

- 在保持 `datafeed -> strategy -> order` 事件驱动架构的基础上，引入**动态参数/动态决策**能力。
- 降低策略逻辑对 LLM 不确定性的影响：做到**可控、可观测、可审计**。
- 兼容现有静态策略代码与 SDK，避免大规模重构。

# 设计原则

- **事件驱动优先**：动态能力以事件为触发，不破坏既有消息链路与吞吐模型。
- **动态与静态解耦**：动态部分专注于参数与信号补充，不直接执行下单。
- **工具调用可控**：严格限流、超时、缓存与审计，避免策略不可控漂移。
- **可回放与可验证**：动态计算结果需要可记录，支持复盘/回测一致性。
- **安全优先**：避免泄露密钥，不在日志输出敏感信息。

# 建议的总体架构（分层）

1. **策略静态层（Static Strategy Code）**
   - 保留现有 Rust/Python 策略逻辑，作为基础信号引擎。
   - 仅在核心逻辑中暴露少量可调参入口（如阈值、仓位系数、风控开关）。

2. **动态参数层（Dynamic Parameter Provider）**
   - 新增 `DynamicParamService`，输入为事件上下文 + 策略元信息。
   - 输出为当次策略执行的**短期参数快照**（例如 30s/1m TTL）。
   - 提供一致性快照与版本号，便于回放与审计。

3. **动态工具层（Agent Tooling Layer）**
   - 由 AI Agent 或规则引擎触发工具调用（行情聚合、链上指标、宏观数据等）。
   - 内置缓存/限流/回退策略，产出结构化特征（Feature）而非直接信号。

4. **策略执行层（Strategy Runner）**
   - Strategy Runner 在消费消息时：先拉取参数快照，再执行静态策略代码。
   - 可选：在静态策略输出基础上进行二次融合（如置信度修正）。

5. **信号发布层（Signal Publisher）**
   - 仍通过 EMQX 主题发布 `SigbotTradeSignal`。
   - 信号中追加 `param_snapshot_id` 以便追踪。

# 关键机制设计

## 1) 动态参数快照

- **触发方式**：基于事件触发生成（与策略执行同步），或提前预热（滑窗刷新）。
- **缓存策略**：在短窗口内复用同一快照，减少 LLM/工具调用频次。
- **一致性**：同一事件/策略执行周期使用同一快照。

## 2) 工具调用治理

- **限流与熔断**：为每种工具定义 QPS 与超时；失败时降级到静态参数。
- **可观测**：记录工具调用耗时、返回质量、失败原因（不含敏感信息）。
- **可复盘**：保存工具输入摘要与输出的 hash。

## 3) 事件驱动兼容

- **不改变触发源**：依旧由 `datafeed` 事件驱动策略执行。
- **将动态结果视为“派生特征”**：作为策略输入数据的一部分，而非独立触发源。
- **可并行预计算**：在 `datafeed` 侧或独立服务做异步预热，避免阻塞主链路。

# 推荐的落地形态

## 方案 A：Strategy Runner 内嵌动态参数获取

- Runner 收到行情事件后调用 `DynamicParamService` 获取快照。
- 优点：最小改造、上下文完整。
- 风险：增加策略执行延迟，需要超时与缓存保障。

## 方案 B：独立 Dynamic Param Service + 预热

- 由独立服务订阅行情事件并持续更新动态参数。
- Runner 仅拉取最新快照（O(1) 查询）。
- 优点：更稳定的延迟和更可控的吞吐。
- 风险：需要对快照时效进行严格版本管理。

# 与 sigbot-researcher 的协同

- Researcher 产出策略时同时输出**动态参数定义**（可调参空间、工具清单）。
- Researcher 的 Fin Auditor 增加对动态参数范围与工具安全性的审计规则。

# 事件驱动限制的优雅处理

- 采用**“事件驱动 + 预计算”**组合：
  - 事件触发执行仍是唯一入口；
  - 动态参数由异步预计算服务更新；
  - Runner 在执行时只读取快照，确保事件驱动不被阻塞。

# 迁移步骤（建议）

1. 在 `types` 中定义 `DynamicParamSnapshot` 结构与版本号字段。
2. 新增 `DynamicParamService`（可在 `strategy` 或 `utils` 子模块）。
3. Strategy Runner 集成快照读取（失败回退到静态参数）。
4. Researcher 输出动态参数定义并更新审计流程。
5. 加入回放与审计日志字段，保障可复盘。

# 风险与缓解

- **LLM 不确定性**：引入“参数范围约束 + 审计阈值 + 回退静态”。
- **性能抖动**：工具调用缓存 + 预热 + 超时保护。
- **回测一致性**：记录快照与输入特征，支持回放。
