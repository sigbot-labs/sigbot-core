# Authguard migration and Helm ownership

Authguard owns authentication, accounts, sessions and grants. Sigbot retains business tenant bindings and accepts only the official SDK's verified, bounded-lifetime request context. The integration pins `authguard-adapter-rust` to commit `56f00ee51a33136dae7e83beba558cdbf05c4a85`. `HeaderAccessContextResolver` verifies the Authguard HMAC signature and expiry; `GrpcAccessContextResolver` resolves opaque scope tokens. Sigbot does not call the SDK's thread-local context functions. Each HTTP request carries a `RequestIdentity` in Axum extensions, and each business handler receives that identity explicitly.

The old local login, JWT issuance, OAuth callbacks, user CRUD, user repositories and process-global `SecurityContext` have been removed. Sigbot has no identity tables or identity migration path. Configure the browser's same-origin `/auth/login`, `/auth/account/security` and `POST /auth/logout` routes through Authguard; do not forward those paths to the Sigbot API.

`authguard` is the typed Sigbot runtime configuration. `provider` is `signed_header` or `grpc`; `service`, `partition`, `region`, `read_action` and `write_action` bind the signed context to the API request. The defaults expect `urn:iam:default:sigbot:global:<tenant>:<request-path-without-leading-slash>` and `sigbot:read` for GET/HEAD, `sigbot:write` for other methods. Configure matching Authguard route policies. A supplied `x-sigbot-tenant-id` must match the signed tenant. Deny grants override allows. Trust cannot be established by supplying an unsigned identity header.

Pass `AUTHGUARD__AUTHZ__SCOPE_DELIVERY__DIRECT_CONTEXT_HMAC_KEY` through a Secret shared with Authguard AuthZ for signed-header delivery. For gRPC use the SDK's `AUTHGUARD_GRPC_TARGET` and `AUTHGUARD_GRPC_TLS` settings and restrict backend network access to the Gateway/workloads. The API refuses to bind without a valid verifier configuration. Worker-only states install a deny-all provider when no verifier is configured, so they do not need Gateway signing keys. No secret values are stored in the chart. Business tenant key custody additionally requires `SIGBOT_SYSTEM_MASTER_KEY`; the previous default master key and JWT-secret fallback are removed.

Workflow APIs are available at `/api/v1/workflows`, `/api/v1/workflows/{id}`, and `POST .../{id}/start` / `stop`. Queries derive `tenant_id` from the authenticated context. A create request supplies a routing/deployment environment and one execution mode (`live`, `paper`, or `backtest`); subsequent updates cannot change the authenticated tenant binding. Responses exclude secret configuration. Start atomically records the immutable graph snapshot in `wf_run` and marks the workflow pending for Controller. Repeated start returns the same active run. Acceptance is not deployment completion or a trade acknowledgement. Raw unscoped workflow queries/deletions fail closed. A worker receives an explicit service tenant, environment and principal identity; absent service identity cannot scan all tenants.

The Helm values have only four top-level groups: `global`, `sigbot`, `middleware`, and `secrets`. `middleware.postgres` is the control-plane PostgreSQL process with TimescaleDB and vector extensions; its image must include both libraries. The extension init script applies to newly initialized databases. Tenant data-plane Redis, pgvector, TimescaleDB, EMQX and object storage are not installed as global platform workloads; they are registered on a scoped `ctl_worker` and reconciled with the nine Workflow components.

`middleware.authguard.enabled` defaults to true. The vendored official OCI dependency is Authguard **1.0.2** and `Chart.lock` is generated by Helm. Authguard keeps its independent secret payload and remains the only IAM owner; Sigbot does not recreate its user, role, permission, or tenant tables. Disable it only when an externally managed, compatible Authguard deployment already owns the Gateway and IAM boundary.

Before installation, use `deploy/helm/sigbot/bootstrap/setup-secret-k8s.sh` (or its AWS/GCP/Vault peer) with an explicit namespace and private Secret env-file. AuthGuard keeps its own independently scoped payload and bootstrap lifecycle. Never commit populated env files. The chart maps one PostgreSQL and Redis credential value into both middleware startup and Sigbot's typed central configuration. Rotating the runtime Secret requires incrementing `secrets.revision` so pods restart. Bootstrap failure aborts installation; values contain only Secret references.

The real public application hostname is an operator input, not an invented default. Set `sigbot.api.gateway.hostnames`, the Authguard Application hosts/HTTPS return URIs and AuthN/Web route hostnames to the same actual origin. Configure cross-namespace Gateway `allowedRoutes` and reference grants when needed. No production hostname or cluster is guessed.

Verification commands:

```bash
helm lint deploy/helm/sigbot
HTTPS_PROXY=http://127.0.0.1:8800 python3 ~/authguard/.agents/skills/authguard-chart-integrator/scripts/validate.py \
  --chart deploy/helm/sigbot --set sigbot.api.enabled=false
cargo test -p sigbot-core --test authguard_integration --test scoped_query --test config_loader
```

The Rust tests cover concurrent request identity isolation, valid signed contexts, invalid signatures, expiry, action/path/tenant mismatch, deny precedence and numeric tenant binding in real SQLite queries. A build or E2E report, rather than this command list, is the evidence that the tests passed in a particular environment.

Configuration accepts canonical `snake_case` only. Duplicate or unknown typed keys fail. Environment variables use the `SIGBOT__` hierarchy, and `${VARIABLE:default}` placeholders are resolved without a shell. Worker and Authguard blocks are strict typed configuration; no alternate key representation is retained.

The UI domain APIs additionally require domain grants under `environment/<env>/{overview,market,connection,notification}/all`; Workflow checks the concrete ID or `new`. This is checked against the SDK's allow/deny patterns in addition to the signed HTTP path grant. Give an operator the explicit domain grants required by that role; a valid session alone is not access to every tenant resource.

Apply `migration/migrate.py` using the database owner's migration credentials before starting the API. Runtime PostgreSQL connections use typed connection options, the configured pool limits, schema and SSL policy; they do not create databases or run DDL. Startup checks that the migration ledger and Workflow tables exist. Runtime credentials should have only the required DML privileges.

`cargo test -p sigbot-core --test authenticated_workflow_api -- --ignored` requires the dedicated migrated `MARKETPULSE_DATABASE_URL`. It starts a real TCP API, signs contexts with the official Authguard SDK, checks tenant/environment/deny isolation against PostgreSQL, and verifies transactional repeated-start behavior. This trusted-gateway boundary test does not replace Hosted Login browser acceptance or actual worker deployment acceptance.

`sigbot.controller.enabled` deploys the central Controller independently from the API. Its service principal scans persisted Workflow scopes; it never borrows a user context. Remote Docker/Kubernetes endpoints, namespace/network isolation, runtime Secret names, egress policy and the whitelisted tenant middleware image/resource specification belong to the scoped `ctl_worker`. The Controller does not read Gateway verifier keys or create remote Secrets. See `src/controller/README.md` for operational bounds and `web/README.md` for real browser gates.
